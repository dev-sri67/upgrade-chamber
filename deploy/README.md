# API and worker deployment on Vultr

This is a reviewable deployment scaffold for the API and its serial worker. The API serves `/healthz` and `/api/profiles`; the worker executes queued runs phase by phase inside Docker containers. No frontend is deployed by these files, and the validated execution profile (Vultr Serverless Inference) is not exercised by either service. Do not present this as the completed public product.

## Prepare the VM

Start with a Vultr Ubuntu 24.04 LTS Cloud Compute VM sized at **4 vCPU / 8 GiB RAM**, then verify the plan's actual availability, current price, and measured resource needs in the Vultr console. Add an SSH key. Use a Vultr firewall group that permits SSH from the operator's address and HTTP/HTTPS on ports 80/443; do not expose port 8000. Point a domain's DNS record to the VM before requesting a public certificate. Vultr's [instance provisioning](https://docs.vultr.com/products/compute/instances/cloud-compute/provisioning) and [firewall](https://docs.vultr.com/products/compute/instances/cloud-compute/networking/enable-firewall) guides describe the current console steps.

On the VM, install Python prerequisites from signed Ubuntu packages. Install Caddy only after choosing a domain and preparing public HTTPS; its packaged service may otherwise start on a public port. Docker must also be installed before the worker can run; bootstrap adds a dedicated worker account to the `docker` group but does not install Docker itself.

```sh
sudo apt-get update
sudo apt-get install -y ca-certificates python3-venv
sudo install -d -m 0755 /opt/uv-0.11.8
sudo python3 -m venv /opt/uv-0.11.8
sudo /opt/uv-0.11.8/bin/python -m pip install --no-deps 'uv==0.11.8'
/opt/uv-0.11.8/bin/uv --version
```

The bootstrap checks this exact uv version and path. Version 0.11.8 is [published on PyPI](https://pypi.org/project/uv/0.11.8/); uv's [lockfile documentation](https://docs.astral.sh/uv/concepts/projects/sync/) describes `uv sync --locked`. Copy a trusted source checkout to the VM without `.env`, `.venv`, caches, or secrets. From that checkout, run:

```sh
sudo bash deploy/bootstrap.sh "$(pwd)"
```

The script accepts only Ubuntu 24.04 and checks for pinned uv. It copies `pyproject.toml`, `uv.lock`, and Python source files under `src/upgrade_chamber/` into root-owned `/opt/upgrade-chamber`; generated bytecode is excluded. It rejects symlinks and unexpected package resources, verifies the source imports both `upgrade_chamber.api` and `upgrade_chamber.worker`, and installs locked production dependencies into `/opt/upgrade-chamber/.venv` using managed Python 3.11. Two unprivileged accounts are created: `upgrade-chamber` for the API (with no Docker group membership) and `upgrade-chamber-worker` for the worker, whose primary group is `upgrade-chamber` and whose only supplemental group is `docker`. Both systemd units are installed under `/etc/systemd/system/`; bootstrap starts or enables nothing. Re-running bootstrap with identical source is supported. If the source differs, it stops before replacing application files; review and prepare an update procedure rather than deleting an existing installation blindly.

## Shared state directory

`/var/lib/upgrade-chamber` holds `runs.db` (the SQLite run queue) and `artifacts/` (the evidence bundle per run). It is owned by `upgrade-chamber:upgrade-chamber` with mode `0770`, and both service units run with `UMask=0007`, so every database and artifact file stays group-writable. This is what lets the API user and the worker user — both in the `upgrade-chamber` group — read and write the same queue and artifact store while neither needs root. The API account is deliberately excluded from the `docker` group; only the worker account may touch the Docker socket.

## Environment files

`/etc/upgrade-chamber/api.env` is root-owned mode `0600`. For run submission it now requires `DATABASE_PATH` (the SQLite path), `ARTIFACT_DIR` (the artifact store path), and `WORKER_IMAGE` (the pinned runner image identity). The optional inference settings stay as before.

`/etc/upgrade-chamber/worker.env` is root-owned mode `0640`. It holds `DATABASE_PATH`, `ARTIFACT_DIR`, and `WORKER_IMAGE` for the worker process. It must never contain inference credentials — the worker owns no inference path.

## Configure inference and HTTPS

Provision a Vultr Serverless Inference subscription using the [current Vultr guide](https://docs.vultr.com/products/compute/serverless-inference/provisioning). Retrieve its inference API key in the console. Available models change; inspect the console's model selector or run the included CLI with the actual subscription key. This CLI calls Vultr's inference endpoint only:

```sh
read -rsp 'Vultr inference key: ' VULTR_INFERENCE_API_KEY; echo
export VULTR_INFERENCE_API_KEY
/opt/upgrade-chamber/.venv/bin/upgrade-chamber-inference models
```

Choose a returned chat model ID and test structured output before configuring the service:

```sh
export VULTR_MODEL_ID='MODEL_ID_FROM_LIST'
/opt/upgrade-chamber/.venv/bin/upgrade-chamber-inference smoke
unset VULTR_INFERENCE_API_KEY VULTR_MODEL_ID
```

Record the selected model and successful smoke result. No model ID or cost is assumed here. [Vultr's inference FAQ](https://docs.vultr.com/products/compute/serverless-inference/faq) points to the current model selector. The API can serve its read-only endpoints and the worker can execute runs without inference credentials, but a real inference smoke test requires them.

Add the verified values to `/etc/upgrade-chamber/api.env` with a root-controlled editor. Use systemd environment-file syntax, one assignment per line: `VULTR_INFERENCE_API_KEY=...` and `VULTR_MODEL_ID=...`, alongside the required `DATABASE_PATH`, `ARTIFACT_DIR`, and `WORKER_IMAGE`. Keep the file owned by root with mode `0600`; do not place secrets in the checkout or Caddyfile.

Copy [Caddyfile.example](Caddyfile.example) to `/etc/caddy/Caddyfile` — it contains the live IP-based demo configuration (see the Public deployment section below for its self-signed caveat). With a real domain, change the site address and drop `tls internal` so Caddy obtains a public certificate. Caddy's [reverse-proxy guide](https://caddyserver.com/docs/quick-starts/reverse-proxy) explains automatic HTTPS once DNS resolves and ports 80/443 reach Caddy. Validate the file and start only after reviewing the configuration:

```sh
sudo apt-get install -y caddy
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl daemon-reload
sudo systemctl start upgrade-chamber-api upgrade-chamber-worker
sudo systemctl enable --now caddy
sudo systemctl reload caddy
curl -fsS http://127.0.0.1:8000/healthz
curl -fsS https://YOUR_DOMAIN.example/healthz
```

Check `systemctl status upgrade-chamber-api`, `systemctl status upgrade-chamber-worker`, and `journalctl -u upgrade-chamber-api -u upgrade-chamber-worker` on failure. The API binds to loopback and runs without Docker access; the worker runs headless and is the only service with Docker socket access. This setup has not been run on a Vultr VM yet; a live HTTPS response and inference smoke call remain deployment gates.

## Public deployment

The demo at `https://45.76.66.244` serves the frontend and proxies the API through Caddy on the VM. This deployment is live, with one caveat stated up front: because no public domain exists, the site uses Caddy's `tls internal` certificate authority. Browsers show a certificate warning when opening `https://45.76.66.244`; the connection is still encrypted, and visitors can inspect the self-signed certificate (issuer `Caddy Local Authority - ECC Intermediate`) and accept it. With a real domain, the `tls internal` line in the Caddyfile is removed so Caddy obtains a publicly trusted certificate automatically.

### Build and upload the frontend

In `web/` (Node 22): `npm install`, then `npm run build`, which produces `web/dist` (`index.html` plus hashed files under `assets/`). The build output is public static data; it ships as plain files:

```sh
tar -cf dist.tar -C web/dist .
scp dist.tar root@45.76.66.244:/tmp/dist.tar
# on the VM:
mkdir -p /var/www/upgrade-chamber
tar -xf /tmp/dist.tar -C /var/www/upgrade-chamber
chown -R root:root /var/www/upgrade-chamber
find /var/www/upgrade-chamber -type d -exec chmod 755 {} +
find /var/www/upgrade-chamber -type f -exec chmod 644 {} +
rm /tmp/dist.tar
```

### Install Caddy and configure it

`apt-get install -y caddy` provides Caddy on Ubuntu 24.04 (version 2.6.2 here) with the packaged systemd unit. Copy [Caddyfile.example](Caddyfile.example) to `/etc/caddy/Caddyfile` — it must use LF line endings. Validate, then start:

```sh
caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
caddy fmt --overwrite /etc/caddy/Caddyfile
systemctl enable --now caddy
```

The Caddyfile serves `/var/www/upgrade-chamber` for the SPA (`try_files {path} /index.html`) and reverse-proxies `/api/*` and `/healthz` to the API at `127.0.0.1:8000`. Security headers: `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`. Caddy's automatic HTTPS also answers plain HTTP on port 80 with a `308 Permanent Redirect` to the HTTPS address.

### Firewall and verification

```sh
ufw allow 80/tcp
ufw allow 443/tcp
ufw status numbered
# from an external machine:
curl -sk https://45.76.66.244/healthz
curl -sk https://45.76.66.244/api/profiles
curl -sk https://45.76.66.244/
```

The API and worker systemd services are untouched by this layer; only Caddy is added and the two firewall ports are opened.
