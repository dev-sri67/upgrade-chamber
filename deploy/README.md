# API scaffold deployment on Vultr

This is a reviewable deployment scaffold for the existing API only. It serves `/healthz` and `/api/profiles`; no run submission, container worker, frontend, or validated execution profile is deployed by these files. Do not present it as the completed public product.

## Prepare the VM

Start with a Vultr Ubuntu 24.04 LTS Cloud Compute VM sized at **4 vCPU / 8 GiB RAM**, then verify the plan's actual availability, current price, and measured resource needs in the Vultr console. Add an SSH key. Use a Vultr firewall group that permits SSH from the operator's address and HTTP/HTTPS on ports 80/443; do not expose port 8000. Point a domain's DNS record to the VM before requesting a public certificate. Vultr's [instance provisioning](https://docs.vultr.com/products/compute/instances/cloud-compute/provisioning) and [firewall](https://docs.vultr.com/products/compute/instances/cloud-compute/networking/enable-firewall) guides describe the current console steps.

On the VM, install Python prerequisites from signed Ubuntu packages. Install Caddy only after choosing a domain and preparing public HTTPS; its packaged service may otherwise start on a public port.

```sh
sudo apt-get update
sudo apt-get install -y ca-certificates python3-venv
sudo install -d -m 0755 /opt/uv-0.11.8
sudo python3 -m venv /opt/uv-0.11.8
sudo /opt/uv-0.11.8/bin/python -m pip install --no-deps 'uv==0.11.8'
/opt/uv-0.11.8/bin/uv --version
```

The bootstrap checks this exact uv version and path. Version 0.11.8 is [published on PyPI](https://pypi.org/project/uv/0.11.8/); uv's [lockfile documentation](https://docs.astral.sh/uv/concepts/projects/sync/) describes `uv sync --locked`. Copy a trusted source checkout to the VM without `.env`, `.venv`, caches, or secrets. From that checkout, run:

```sh
sudo bash deploy/bootstrap.sh "$(pwd)"
```

The script accepts only Ubuntu 24.04 and checks for pinned uv. It copies `pyproject.toml`, `uv.lock`, and Python source files under `src/upgrade_chamber/` into root-owned `/opt/upgrade-chamber`; generated bytecode is excluded. It rejects symlinks and unexpected package resources, creates an unprivileged `upgrade-chamber` account with no Docker group, and installs locked production dependencies into `/opt/upgrade-chamber/.venv` using managed Python 3.11. `/var/lib/upgrade-chamber` is service-writable; `/etc/upgrade-chamber/api.env` is root-owned mode `0600`. The systemd manager reads that environment file before launching the unprivileged service. Re-running bootstrap with identical source is supported. If the source differs, it stops before replacing application files; review and prepare an update procedure rather than deleting an existing installation blindly.

## Configure inference and HTTPS

Provision a Vultr Serverless Inference subscription using the [current Vultr guide](https://docs.vultr.com/products/compute/serverless-inference/provisioning). Retrieve its inference API key in the console. Available models change; inspect the console's model selector or run the included CLI with the actual subscription key. This CLI calls Vultr's inference endpoint only:

```sh
read -rsp 'Vultr inference key: ' VULTR_INFERENCE_API_KEY; echo
export VULTR_INFERENCE_API_KEY
/opt/upgrade-chamber/.venv/bin/upgrade-chamber-inference models
```

Choose a returned chat model ID and test structured output before configuring the service:

```sh
export VULTR_MODEL_ID='MODEL_ID_FROM_LIST'
/opt/upgrade-chamber/.venv/bin/upgrade-chamber-inference smoke
unset VULTR_INFERENCE_API_KEY VULTR_MODEL_ID
```

Record the selected model and successful smoke result. No model ID or cost is assumed here. [Vultr's inference FAQ](https://docs.vultr.com/products/compute/serverless-inference/faq) points to the current model selector. The API scaffold can serve its read-only endpoints without inference credentials, but a real inference smoke test requires them.

Add the verified values to `/etc/upgrade-chamber/api.env` with a root-controlled editor. Use systemd environment-file syntax, one assignment per line: `VULTR_INFERENCE_API_KEY=...` and `VULTR_MODEL_ID=...`. Keep the file owned by root with mode `0600`; do not place secrets in the checkout or Caddyfile.

Replace `YOUR_DOMAIN.example` in [Caddyfile.example](Caddyfile.example) with the operator's domain, then install the result as `/etc/caddy/Caddyfile`. Caddy's [reverse-proxy guide](https://caddyserver.com/docs/quick-starts/reverse-proxy) explains automatic HTTPS once DNS resolves and ports 80/443 reach Caddy. Validate the file and start only after reviewing the configuration:

```sh
sudo apt-get install -y caddy
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl daemon-reload
sudo systemctl enable --now upgrade-chamber-api
sudo systemctl enable --now caddy
sudo systemctl reload caddy
curl -fsS http://127.0.0.1:8000/healthz
curl -fsS https://YOUR_DOMAIN.example/healthz
```

Check `systemctl status upgrade-chamber-api` and `journalctl -u upgrade-chamber-api` on failure. The service binds to loopback and runs without Docker access. This setup has not been run on a Vultr VM yet; a live HTTPS response and inference smoke call remain deployment gates.
